# Лабораторная работа №5 — Portainer

Веб-интерфейс управления Swarm-кластером: контейнеры, образы, сети, тома, журналы и
потребление ресурсов без работы через командную строку.

## Два способа развернуть

### 1. Один сервис на manager-ноде (как в методических указаниях)

```bash
bash deploy/lab5/deploy_portainer.sh
```

Скрипт проверяет, что узел является manager-нодой, и создаёт сервис, повторный запуск
обновляет образ вместо падения с ошибкой.

### 2. Сервер плюс агенты на каждой ноде (рекомендуется)

```bash
docker stack deploy -c deploy/lab5/portainer-agent-stack.yml portainer
```

Одиночный Portainer видит только ту ноду, где он запущен: он общается с локальным
`docker.sock`. Агент в режиме `global` поднимается на каждой ноде и передаёт серверу данные
о контейнерах и ресурсах воркеров. Для задания, где нужно собрать информацию о нодах
и о потреблении ресурсов сервисов, подходит именно этот вариант.

## Первый вход

1. Открыть `http://192.168.xx.11:9000`.
2. Создать учётную запись администратора. Пароль не менее 12 символов.
3. Выбрать окружение `primary`.

Учётную запись нужно создать в течение нескольких минут после запуска: в целях безопасности
Portainer блокирует первоначальную настройку, если её долго не выполняют. Если это произошло,
сервис перезапускается командой `docker service update --force portainer`.

## Что посмотреть по пунктам задания

| Пункт | Где смотреть |
|---|---|
| Информация о нодах: память, процессоры | Swarm → Details, таблица нод с CPU и RAM |
| Использовать запущенный стек | Stacks → `t2` из работы №4 |
| Логи работы сервисов | Services → `t2_app` → Service logs |
| Потребление ресурсов | Containers → выбрать контейнер → Stats, графики CPU, памяти, сети и диска |
| Причины сбоев | Services → `t2_app` → Tasks, столбцы состояния и ошибки |

Полезный сценарий для отчёта: остановить одну реплику и показать в Portainer, как Swarm
поднимает замену, а в задаче остаётся запись о причине остановки.

## Безопасность

Portainer монтирует `/var/run/docker.sock`, то есть получает полный контроль над демоном
Docker. В реальной эксплуатации это означает:

- доступ к интерфейсу только из внутренней сети или через VPN, не наружу;
- отдельные учётные записи с ролями вместо общего администратора;
- обязательный HTTPS, если интерфейс выходит за пределы сегмента.

Это прямая мера против риска №8 реестра из работы №1: ошибочные действия персонала.

## Что приложить к отчёту

1. Главная страница со списком окружений и сводкой по кластеру.
2. Swarm → Details: три ноды с объёмом памяти и числом процессоров.
3. Список стеков с развёрнутым `t2`.
4. Сервисы стека с числом реплик и опубликованными портами.
5. Журнал сервиса `t2_app`.
6. Графики потребления ресурсов контейнера.
7. Таблица задач с причиной сбоя, если он был.

# Лабораторная работа №6 — Prometheus и Grafana

Сбор метрик с трёх нод Swarm-кластера и визуализация в Grafana. Кроме метрик узлов
собираются метрики самого портала t2, поэтому на дашборде видно, как балансировщик
распределяет запросы между нодами.

## Состав

| Файл | Назначение |
|---|---|
| `monitoring-stack.yml` | стек: Prometheus, node-exporter, Grafana |
| `prometheus.yml` | цели сбора метрик |
| `alerts.yml` | шесть правил оповещений |
| `grafana/datasource.yml` | автоподключение Prometheus как источника данных |
| `grafana/dashboards.yml` | автозагрузка дашбордов из каталога |
| `grafana/t2-overview.json` | дашборд на десять панелей |

## Развёртывание

Выполняется на manager-ноде:

```bash
bash deploy/lab6/deploy.sh
```

Скрипт проверяет, что сеть стека из работы №4 существует. Если той работы ещё нет,
он создаёт пустую overlay-сеть с тем же именем, чтобы мониторинг поднялся: цель
`t2_app` будет просто помечена как недоступная. Без этой проверки `docker stack deploy`
падает с невнятным сообщением о ненайденной сети.

Вручную:

```bash
cd deploy/lab6
docker stack deploy -c monitoring-stack.yml monitoring
docker stack services monitoring
```

Дальше:

- Prometheus — `http://192.168.xx.11:9090`
- Grafana — `http://192.168.xx.11:3000`, логин `admin`, пароль `admin`

Источник данных и дашборд подключаются сами. Если по заданию нужно показать ручную
настройку, она делается так: Connections → Data Sources → Add data source → Prometheus →
URL `http://prometheus:9090` → Save & Test.

Пароль администратора Grafana задаётся при развёртывании:

```bash
GF_PASSWORD='надёжный-пароль' docker stack deploy -c monitoring-stack.yml monitoring
```

## Три решения, которые стоит объяснить на защите

### Обнаружение целей через DNS вместо списка адресов

В методических указаниях адреса нод прописаны вручную. Здесь используется механизм Swarm:
имя `tasks.node-exporter` резолвится в адреса всех задач сервиса. Node-exporter запущен
в режиме `global`, то есть по одному экземпляру на каждой ноде, и список целей обновляется
сам при добавлении или выводе ноды. Вариант со статическими адресами оставлен в
`prometheus.yml` закомментированным.

### Публикация порта экспортера в режиме host

```yaml
ports:
  - target: 9100
    published: 9100
    mode: host
```

При обычном режиме `ingress` запрос к `192.168.xx.12:9100` мог бы уйти через общую сеть
кластера на экспортер другой ноды, и метрики разных машин перемешались бы. Режим `host`
привязывает порт к конкретной ноде.

### Монтирование хозяйской файловой системы в экспортер

```yaml
volumes:
  - /proc:/host/proc:ro
  - /sys:/host/sys:ro
  - /:/host/root:ro
```

Без этих монтирований node-exporter отдаёт метрики собственного контейнера, а не машины,
и цифры по диску и памяти не имеют смысла.

## Метрики приложения

Портал отдаёт свои метрики на `/api/metrics`. Каждая серия помечена идентификатором ноды:

```
t2_http_requests_total{endpoint="/api/v1/instance",instance_id="node2-1",method="GET",status="200"}
t2_http_request_duration_seconds_bucket{endpoint="/",instance_id="node3-1",le="0.05"}
t2_instance_info{hostname="a7bf72ad0673",instance_id="node2-1"}
```

Полезные запросы PromQL для отчёта:

```promql
# сколько запросов обработала каждая нода
sum by (instance_id) (t2_http_requests_total)

# распределение нагрузки в реальном времени
sum by (instance_id) (rate(t2_http_requests_total[1m]))

# живые экземпляры портала
count(up{job="t2_app"} == 1)

# 95-й перцентиль времени ответа по нодам
histogram_quantile(0.95, sum by (le, instance_id) (rate(t2_http_request_duration_seconds_bucket[5m])))
```

Чтобы Prometheus видел приложение, его контейнер подключён к сети стека из работы №4.
Если стек `t2` развёрнут под другим именем, имя сети задаётся переменной:

```bash
T2_NETWORK=мойстек_t2net docker stack deploy -c monitoring-stack.yml monitoring
```

Если работа №4 не разворачивалась, достаточно создать пустую сеть с тем же именем —
это и делает `deploy.sh`:

```bash
docker network create --driver overlay --attachable t2_t2net
```

## Дашборд

Папка `t2`, дашборд «t2 — портал и кластер», десять панелей:

1. Живых экземпляров портала
2. Нод в кластере
3. Запросов в секунду
4. Доля запросов по нодам, кольцевая диаграмма
5. Запросы по нодам
6. Ответы по кодам
7. Длительность запроса, 95-й перцентиль
8. Топ маршрутов по нагрузке
9. Загрузка процессора по нодам
10. Занятая память по нодам

Готовый дашборд сообщества для узлов — **Node Exporter Full**, идентификатор **1860**,
добавляется через Dashboards → Import.

## Правила оповещений

| Правило | Условие | Какой риск закрывает |
|---|---|---|
| `NodeDown` | нода не отвечает минуту | отказ узла |
| `DiskAlmostFull` | диск заполнен более чем на 80% | риск 9 реестра из работы №1 |
| `HighMemoryUsage` | занято более 90% памяти | деградация под нагрузкой |
| `AppInstanceDown` | экземпляр портала не отдаёт метрики | отказ реплики |
| `TooFewAppInstances` | живых экземпляров меньше двух | балансировать нечего |
| `HighErrorRate` | более 5% ответов с кодом 5xx | битый релиз |

Состояние правил: `http://192.168.xx.11:9090/alerts`.

В правиле `TooFewAppInstances` выражение обёрнуто в `or vector(0)`. Без этого при полном
отказе всех экземпляров функция `count()` по пустому множеству возвращает не ноль,
а пустоту, и правило молчит ровно в той ситуации, ради которой написано. Проверено:
после остановки всех реплик оповещение переходит в состояние `firing`.

Отправку оповещений в мессенджер выполняет Alertmanager, в этой работе он не разворачивается.

## Изменение конфигурации

Объекты `config` в Swarm неизменяемы. После правки `prometheus.yml` или `alerts.yml`
нужно поднять версию в именах внутри `monitoring-stack.yml`, иначе Swarm продолжит
использовать старое содержимое:

```
prometheus_config_v1  →  prometheus_config_v2
```

Либо удалить стек целиком и развернуть заново: `docker stack rm monitoring`.

## Проверка

```bash
# цели: все должны быть в состоянии up
curl -s http://192.168.xx.11:9090/api/v1/targets | grep -o '"health":"[a-z]*"'

# метрики узлов по каждой ноде
curl http://192.168.xx.11:9100/metrics
curl http://192.168.xx.12:9100/metrics
curl http://192.168.xx.13:9100/metrics

# распределение запросов между нодами
curl -s --get http://192.168.xx.11:9090/api/v1/query \
  --data-urlencode 'query=sum by (instance_id) (t2_http_requests_total)'
```

## Что приложить к отчёту

1. Страница Targets в Prometheus: все цели `up`, три ноды в задании `node_exporter`.
2. Страница Alerts со списком правил.
3. Дашборд Grafana целиком.
4. Панель «Доля запросов по нодам» с примерно равными долями.
5. Та же панель после остановки одной реплики: её линия падает в ноль, остальные забирают нагрузку.
6. Панели загрузки процессора и памяти по трём нодам.
7. Вывод `curl` с метриками приложения, где виден `instance_id`.
